# 从入门到能面试：六周吃透这套性能基线门禁

> **写给谁**：能把 Python 写顺、知道 pytest 是干什么的，但**没做过性能测试**，也没独立设计过一个有门禁的测试平台。
> **六个月不行吗**：这套东西的知识面不宽 —— 它窄，但每一步都有"为什么不能那样做"的坑。六周按每步都动手算，够了；只想读不想跑，两周也能读完，但你面试时说不清细节。
> **配套读本**：`docs/初学者完全入门.md`（讲代码怎么连起来）和 `README.md`（讲结论）。本文只安排**顺序**和**每一步该动手做什么**。

## 开始之前：先花 20 分钟把环境跑起来

不跑起来的话，后面六周全是纸上谈兵。

```powershell
# Windows / PowerShell，仓库根目录
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt -r requirements-dev.txt

# 跑平台自身测试：370 passed / 19 skipped，约 130 秒
# 那 19 条 skip 是"缺 Redis / MySQL 容器"，不是失败
& ".\.venv\Scripts\python.exe" -m pytest tests/ -q

# 跑一轮真压测 + 门禁：约 1 分钟
& ".\.venv\Scripts\python.exe" platform_cli.py run --label first --items 20000 --step-users 10 20 --step-duration 8 --set-baseline
```

第二和第三条命令的输出**先留着别关**。第 1 周你会反复回来看它们。

> **踩坑预警（Windows）**：如果 `pytest` 报 `PermissionError: [WinError 5]` 且路径里有 `pytest-of-<用户名>`，那是 Windows 临时目录权限问题，与本仓库无关。换一个 `TMP` 指向的目录，或者在 WSL / Linux 里跑都行。

## 第 1 周 · 先建立"数字会骗人"的直觉

**这周的目标不是学工具，是把你的默认信任打掉。**

`README.md` 的第一章（第 52 行起）有七个实测案例。**不要当结论读，当实验读**：每一个都给了复现命令，跑一遍。

必做三件事：

1. **跑 `python platform_cli.py probe --items 400 --step-users 2 --step-duration 1`**
   它会同时跑 `mode=agg` 和 `mode=n1` 两种实现，把两者的 P95 并排打出来。看清同一份业务逻辑，差了将近 8 倍。
   代码在 `sut/app.py:321`（`slow_by_supplier`），`mode=n1` 那个分支是**故意写成 N+1 的** —— 它不是 bug，是标本。
2. **读 `docs/诚实边界.md` 的前两节**（1–65 行，绝对数字不能外推 / 单机引擎是天花板）。里面的每个数字都标了机器和日期。数一数它**拒绝**了多少种说法。
3. **自己造一个"假结论"**：拿 `run` 的输出，把 P95 当"用户感受的耗时"讲给你的朋友听，然后翻到 `docs/度量口径.md:446`（混合 P95 ≠ 单请求耗时），看你在哪一步说错了。

**这周的验收标准**：你能不看文档说出"为什么单机压测的绝对 rps 不能写成 skill 里"。

**如果只有 5 小时**：只做第 1、2 项，第 3 项留到第 4 周。

## 第 2 周 · 读引擎：分位数是怎么算出来的

这周进 `bench/`，三个文件共 1237 行（`engine.py` 389 / `scenarios.py` 362 / `distributed.py` 486）。**它短，但每一行都在回答一个"如果不这样会怎样"。**

按这个顺序读，每读一个函数就手抄一遍核心表达式：

| 顺序 | 位置 | 你要能回答的问题 |
|---|---|---|
| 1 | `bench/engine.py:43` `percentile` | 为什么 `idx = ceil(q/100*n) - 1` 而不是线性插值？N<20 时 P95 是什么？ |
| 2 | `bench/engine.py:65` `Sample` / `:75` `Stats` | 为什么 `Sample` 里有 `at`（时间戳）？谁盖的？ |
| 3 | `bench/engine.py:102` `summarize` | 热身样本怎么丢？丢完一条不剩时发生了什么？（看 `:342` 的 `if kept:`） |
| 4 | `bench/engine.py:189` `Runner` | 类文档里那段"为什么刻意没有 `timeout_s`"讲了什么事故？ |
| 5 | `bench/engine.py:313` `run` | `spawn_step = ramp_up_s / users`（`:323`）是为了什么？ |
| 6 | `bench/scenarios.py:333` `bind` | 为什么不直接用闭包，要显式传参？ |
| 7 | `bench/scenarios.py:23` `DEFAULT_MIX` | 写路径只占 5%，为什么不能是 0？ |

**动手**（这周的动手比读重要）：

1. **验证 nearest-rank 的推论**：写个 10 行脚本，喂 19 个样本给 `percentile`，看 `p95` 是否等于 `max`。这条性质**已经有**用例钉住了（`tests/test_engine.py:76` `test_percentile_is_not_interpolated`）。下一步才是重点：**把 `bench/engine.py:43` 的实现改成线性插值，跑测试，看哪条红** —— 你应该看到 `test_percentile_is_not_interpolated` 与 `test_percentile_returns_observed_value` 一起变红。这两条就是"不插值"这个决定的全部防线。
2. **跑一次 `--step-users 1` 的压测**（`--step-duration 5` 就够），看 `max_inflight`。为什么它应该恰好是 1？如果它跑到 2 了说明什么？
3. **把 `_rnd()` 改回每次 `random.Random()`**（`bench/scenarios.py:69` 附近），再跑一遍看 `test_engine_runner.py` 哪条红。想想为什么原来那条注释"每个线程各自持有一个 Random"是假的。

**这周的验收标准**：给你 20 个数字，你能手算出 P50/P95/P99，并说出"这 20 个数算出来的 P99 有什么道理不值得信"。

**最容易滑过去的地方**：`summarize` 里那个 `if kept:` 兜底（`bench/engine.py:342`）。没有它，`Stats.total == 0`，下游所有分位数都是 0，你会得到一个"快得不可思议"的假结果。**去把它删掉试试，看有几个用例能抓到。**

> 写这份路线时我实测过：删掉兜底、跑全量 369 条用例，**全绿**。也就是说这个兜底当时没有任何用例守着 —— 它只在 `warmup_drop_s >= duration_s` 这种异常配置下才触发，而默认配置永远走不到。所以我补了一条 `tests/test_engine_runner.py::test_warmup_drop_never_empties_the_sample_set`，并做了承重验证（删兜底 → 该用例 FAILED，拿到 `total=0`；加回 → 15 passed）。
>
> **这一件事值得单独记住**：一个防御性分支如果只在"异常配置"下执行，那么所有走正常路径的用例都碰不到它。**变异测试是发现这类缺口的唯一办法** —— 不是"再读一遍代码"，是"把它改坏，看谁叫"。

## 第 3 周 · 口径：同一份数据为什么能得出三个 P95

这周全部在 `metrics/analysis.py`（约 720 行），并且只精读 `merge_step_rows`（第 445 行）一个函数。

**它值得单独一周。** 历史上这里出过三个独立的事故：

| 事故 | 表现 | 现在的写法 |
|---|---|---|
| 尾比各自取 max | 真实 6.00 的尾比被稀释成 1.50 → **漏报** | `worst_tail = max((p99/p95, p95, p99) for r in rows)` 一次拿到成对的值 |
| RPS 各梯度相加 | 370 rps 变成 740 | `total / duration`，不相加 |
| `run` 池化 vs `gate` 取最差梯度 | 同一 run 两个 P95（105.9 / 128.9） | 全平台只有这一个出口 |

**动手**：

1. 打开 `merge_step_rows` 的文档字符串，它有三段。**逐段找出它对应的是上表哪一行事故。**
2. 造两组梯度数据手算：`[{p95:100, p99:400}, {p95:200, p99:300}]`。分别用"各自取 max"和"比值最大那组"算尾比，得到 4.0 和 1.5。**这就是那个 6.00→1.50 的缩小版。** 然后去 `metrics/analysis.py:513` 看 `worst_tail` 那一行 —— 注意它用元组一次 `max`，而不是三个独立 `max`，这是唯一能让"成对"成立且写起来不难看的做法。
3. 跑 `python platform_cli.py trend --label first`，看它怎么判断"涨了还是跌了"。再去 `metrics/analysis.py:252` 看 `compare_to_baseline` —— **为什么延迟涨了算劣化、rps 跌了算劣化，两个方向相反？**
4. 读 `check_comparability`（`:198`）。它返回四种 verdict，其中哪种是"我没法判"？

**这周的验收标准**：你能解释"为什么 `metrics/analysis.py` 里这个函数被三个地方调用（`platform_cli`、`dashboard`、`report`），而它们必须调同一个"。

**补充读物**：`docs/度量口径.md` 第一到第三节。那三节比代码更啰嗦，但把"为什么"讲全了。

## 第 4 周 · 门禁：一条规则怎么写才不会被绕过

`metrics/gate.py`（约 700 行）+ `gate_rules.yaml`（73 行）。先读 yaml，它短，五个段一眼看完。

**核心不是 12 条规则，是 `RuleResult` 那几个字段**（`metrics/gate.py:40`）：

```python
@dataclass
class RuleResult:
    rule_id: str
    passed: bool
    skipped: bool = False   # ← :59，这个字段是全部设计的重心
    severity: str           # blocking / warning
    ...
```

`GateReport.blocked` 在 `:89`，返回值那一行（`:91`）是
`any((not r.passed) and r.severity == BLOCKING and not r.skipped for r in self.results)` ——
**三个条件缺一不可**，其中 `and not r.skipped` 就是"跳过不许当通过"那一句。

**动手，按这个顺序，每条都要亲手改坏再改回来**：

1. **让 `skipped` 失效**：把 `GateReport.blocked` 里的 `and not r.skipped` 删掉。跑测试。想想为什么"跳过"和"通过"在报告里长得一样，而它们意思正好相反。
2. **让 0 个用例变成 100%**：把 `evaluate_suite` 里的通过率改回 `(passed / total) if total else 1.0`。看 `test_rules_single_source.py` 和 S1 的用例怎么反应。
3. **让 `severity` 只有两档的意义消失**：把某条 warning 规则改成 blocking。跑 `test_platform.py`，看有没有用例挡住你。**如果没有，就找到那个缺口。**
4. **看 `docs/已知问题.md` 的 P-16**：R3 的判据被 runner 噪声淹没，作者选择"如实降级"而不是调阈值糊过去。**这是这周最重要的一课：门禁也会说谎，说真话比好看重要。**

**这周的验收标准**：有人问你"你这个门禁能被人绕过吗"，你答得出三条具体路径，以及为什么现在每条都被挡住了（或没被挡住、但写在了已知问题里）。

**进阶**：读 `docs/度量口径.md` 第五节（三档 severity 与"每条规则都要有行动指引"）。然后去 `tests/test_platform.py:461` 找 `test_every_rule_carries_an_action` —— 它保证新加规则忘了写 `action` 就会红。

## 第 5 周 · 存储与闭环：基线怎么活着离开这台机器

这周跨三个文件：`metrics/store.py`（466 行）、`metrics/baseline.py`（131 行）、`metrics/pytest_plugin.py`（172 行）。

**问题很具体**：CI 的 runner 是临时的，跑完就没了。基线怎么跟过去？

**动手**：

1. **画出五张表的关系**（`runs` / `steps` / `cases` / `baselines` / `gate_results`）。`init_db` 在 `metrics/store.py:147`。注意 `cases.run_id`（`:73`）与 `steps.run_id`（`:51`）都带 `REFERENCES runs(run_id) ON DELETE CASCADE` —— 这就是 P-26 那条"插件独立跑撞外键"的物理成因。
2. **理解"基线只能由人写"**：跑 `grep -rn "set_baseline(" --include=*.py .`，确认**生产路径只有两处** —— `platform_cli.py:297`（`run --set-baseline`）和 `platform_cli.py:737`（`baseline set`），另有 `metrics/baseline.py:124` 是 `baseline import` 的内部调用。除此之外没有任何自动路径。**为什么这条很重要**（提示：如果每轮自动覆盖基线，"慢慢变慢"会被每一轮自己批准）。
3. **走一遍完整闭环**（下面每条都实测过，参数名照抄即可）：
   ```powershell
   # A. 本机跑一轮并显式设基线
   python platform_cli.py run --label w5 --items 400 --step-users 3 --step-duration 2 --set-baseline

   # B. 把基线导出成文件（--file 可省，省了打 stdout）
   python platform_cli.py baseline export --label w5 --file snap.json

   # C. 换一台机器 / 换一个空库，从文件恢复
   $env:QUALITY_DB = "另一个路径\q.db"
   python platform_cli.py baseline import --label w5 --file snap.json
   python platform_cli.py baseline show --label w5

   # D. 在新库里再跑一轮，让门禁拿它做对比
   python platform_cli.py run --label w5 --items 400 --step-users 3 --step-duration 2
   python platform_cli.py gate --run-id <上面打出的 run_id>
   ```
   注意 `--kind` 参数（`perf` / `probe`）。**如果你忘了它，probe 轮的 R3 会静默 SKIP** —— 这是 P-20/P-21 那两条缺陷的现场。
   `baseline import` 会主动提醒"该基线量于哪台机器、本轮是哪台机器"—— 因为机器不同时绝对值不可直接比。
4. **读 `metrics/pytest_plugin.py` 的"没设 `QUALITY_RUN_ID` 时完全静默"**。为什么一个插件要能被完全关掉？

**这周的验收标准**：你能在白板上画出"本机跑一轮 → 导出基线 → CI 上导入 → 新轮次对比"的全链路，并指出哪一步是**人必须介入**的。

**踩坑记录**：给一轮 run 造数据时只 `add_steps` 不够，`_run_metrics` 读的是 `runs.metrics_json`，必须再 `finish_run(...)`。这个坑我在改 P-21 那批缺陷时踩过一次。

## 第 6 周 · 自己造一个缺陷，让门禁抓住它

前五周都是"读 + 验证别人写的"。这周反过来：**你加一个慢查询，然后让门禁拦住它。**

完整任务（约 8–12 小时）：

1. **注入**：在 `sut/app.py` 里加一个端点，故意写出 N+1 或全表扫描（照 `slow_by_supplier` 的 `mode=n1` 分支抄）。
2. **写场景**：在 `bench/scenarios.py` 里加一个场景函数，并在 `build_mix` 里给它一个权重。
3. **让门禁能看见它**：跑一轮压测，确认 P95 真的变慢了。如果没有，说明数据量不够（回去看 `docs/诚实边界.md` 第四节：性能探针的数据量必须接近真实规模）。
4. **补测试**：
   - 一条**行为**用例（调端点、断言数据对）
   - 一条**回归**用例（钉住"这个场景必须被 mix 包含"，否则以后有人删了它，门禁就永远看不见这个慢查询了）
5. **做承重验证**：把你的修复/加的断言**回退掉**，确认用例真的会红。**这一步不能省** —— 一个从没红过的用例，你无法证明它在测任何东西。
6. **写进 `docs/已知问题.md`**：按 P-1~P-27 的格式，写清状态 / 位置 / 机制 / 实测数字 / 修复 / 承重验证 / 教训。

**这周的验收标准**：`git diff` 里有一个新缺陷、一个新场景、两条新用例、一条新台账，而且你能对着 diff 讲 5 分钟。

**如果你只做一件事**：做第 5 步。它是这套仓库所有测试的共同信念 —— `docs/已知问题.md` 里 26 条缺陷，**每条都写了承重验证怎么做**。

## 面试时会被问到的七个问题

这些是这套仓库最容易被追问的地方。**每个都能在这里找到答案，但你要用自己的话说。**

1. **「你这个 P95 是怎么算的？」**
   → nearest-rank，不插值（`bench/engine.py:43`）。理由是"永远返回一个真实观测到的值"。代价是 N<20 时 P95 就是最大值 —— 所以我另有一条规则（R4/P3）专门卡样本量。

2. **「同一个系统为什么会有两个 P95？」**
   → 一个是池化（所有样本一起算），一个是取最差梯度。**两个都输出**，因为"整体健康"和"最差时刻"是两个问题。历史上这里出过事故：`run` 用一个口径、`gate` 用另一个，同一轮跑出两个数。

3. **「你怎么保证门禁不是摆设？」**
   → 三个机制：规则有退出码（CI 能真的拦）、`skipped` 与 `passed` 严格区分、`scripts/demo.py` 把"绿→注入→红→恢复绿"四幕做成一条命令（12 秒可复现）。

4. **「基线会不会被慢慢污染？」**
   → 基线只能由人显式设置，没有任何自动覆盖路径。这是刻意的：自动覆盖等于让"慢慢变慢"每轮自己批准。

5. **「你的数字能外推到别的机器吗？」**
   → 绝对数字不能，比例关系可以。`docs/诚实边界.md` 整份文档都在划这条线，包括一条"实测把方向也证伪了"的自我更正。

6. **「有没有你测了但其实没测出来的东西？」**
   → 有，写在 `docs/已知问题.md` 的 P-16：R3 的判据被 runner 噪声淹没，所以 CI 上它是 advisory（只报数不拦人）。**阈值一个字没改，只降了 severity** —— 因为改阈值等于掩盖。

7. **「这套东西最大的坑是什么？」**
   → **静默跳过**。P-20 那条：`gate` 把基线 kind 写死成 `perf`，probe 轮的 R3 从来没生效过，而它表现为 `[SKIP]` + 退出码 0。报错会被修，跳过会被当成正常。

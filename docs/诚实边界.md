# 诚实边界

这个文件说明**这套平台能证明什么、不能证明什么**。

它不是免责声明，是使用说明。**越界解读比没有数据更危险** ——
一份"P95 = 397ms"的报告，配上错误的适用范围，会变成一次
基于错误信心的架构决策。

---

## 一、绝对数字不能外推，比例关系可以

### 不能做的

- ❌ 拿本机的 RPS 数字做容量规划
- ❌ 拿本机的 P95 断言"生产环境会遇到 X ms"
- ❌ 对比本机数字和别人的 benchmark 报告

### 可以做的

- ✅ 同一个接口两种实现的**比例**（N+1 比聚合慢 5.7×）
- ✅ 改前改后的**相对变化**（这次提交让 P95 劣化了 30%）
- ✅ 不同场景之间的**排序**（写路径比读路径慢一个数量级）

### 原因

压测机与被测服务**跑在同一台机器、抢同一份 CPU**。
自研引擎是进程内线程池，被测服务也是本机进程 —— 两边互相干扰。

真实容量会比这里高（服务能独占资源）。
但两个接口之间的相对开销是真实的，因为干扰对双方是均等的。

---

## 二、单机引擎是天花板：没有分布式能力

自研引擎（`bench/engine.py`）用 `ThreadPoolExecutor` 在本机发起压测。

**这意味着：**

- 压到几千并发时，瓶颈很可能是**压测机自己**，不是被测服务；
- 单机线程池到不了生产级别的压力上限（万级并发需要分布式压测集群）。

**平台自己的应对：** `Runner` 会采样实际在途请求数（`max_inflight`），
当"实际在途 < 配置并发的一半"时会提示**瓶颈在压测机**。

实测中每个梯度的 `inflight` 都等于配置并发（10u → inflight=10，
20u → inflight=20），说明**在本次实测的压力范围内**压测机还不是瓶颈。
但这是"本次实测范围内"的结论，不是"这个引擎永远够用"。

## 三、SQLite：写路径的数字完全没有参考价值

这是本项目**最容易被误读**的一组数字。

### 现象

10 并发混合压测下：

| 场景 | RPS | P95 | P99 |
|---|---:|---:|---:|
| `item_detail`（读） | 843 | 36.0 ms | 61.5 ms |
| `stock_write`（写） | **66** | 403.9 ms | **915.5 ms** |

写路径比读路径慢一个数量级以上。

### 但这不是"代码写得差"

瓶颈是 **SQLite 的单写者模型**：写操作走 `BEGIN IMMEDIATE`
（独占写锁），写请求之间**必须串行化**。并发再高也不会变快，
只会让更多请求排队。

### 所以

- ❌ 不能说"这个应用的写接口性能有问题" —— 换 MySQL/PostgreSQL 后
  写并发模型完全不同，这组数字**没有参考价值**；
- ✅ 可以说"在 SQLite 上，写路径是不可外推的瓶颈，容量评估必须
  在有真实数据库的环境里重做"。

**这条边界本身是有价值的结论** —— 它防止有人拿这组数字去
优化应用代码（那样做会一无所获，因为瓶颈不在代码里）。

## 四、性能探针的数据量必须接近真实规模

### 同代码、同机器、只换数据量

| 数据量 | `agg` | `n1` | 比值 |
|---:|---:|---:|---:|
| 800 | 31.7 ms | 32.4 ms | **1.02×** |
| 2 000 | 6.0 ms | 17.7 ms | 2.94× |
| 20 000 | 38.2 ms | 219.2 ms | 5.73× |

N+1 的代价正比于"每个供应商下挂的物料数"。
800 条时每个供应商下只有 20 个物料，多查 20 次被 SQLite 页缓存
完全吸收，**缺陷基本不可见**。

### 所以

- ❌ 不能用小数据量的绿灯证明"没有性能问题"；
- ✅ 性能用例的数据量要接近真实规模（本项目用 20 000 条）；
- ✅ 功能用例可以继续用小数据量（800 条，跑得快）——
  但要清楚它**只验证功能，不验证性能**。

这也是性能探针从功能用例中拆出来单列 `tests/test_probes.py` 的原因。

## 五、测量方法本身会改变结论

### 不热身 vs 热身

同一个"报表比点查慢 5 倍"的断言：

```
不热身、不复用连接：点查 15.7 ms / 报表 47.2 ms   → 3.0×   ❌ 红
热身 3 次 + Session：点查  3.6 ms / 报表 38.2 ms   → 10.7×  ✅ 绿
```

差别全在**分母**。冷启动时每个接口背约 12ms 固定成本
（TCP 建连 + 页缓存冷 + uvicorn 惰性导入），
这个成本加在 3.6ms 的点查上占比远大于加在 38ms 的报表上，
**比例被系统性地压低了**。

### 所以

- ❌ 不要用"没热身的一次测量"去否定或肯定一个比例型结论；
- ✅ 比例型断言对测量方法极度敏感，热身、连接复用、样本量
  都要在报告里写清楚，否则数字不可复现；
- ✅ 当断言和预期不符时，**先怀疑测量方法，再怀疑被测对象**
  （本项目的三条探针里有两条最初都是测量方法的问题，不是服务的问题）。

## 六、混合场景分位数不能和单请求耗时比较

```
单请求（无并发）：  报表 ≈ 38 ms，点查 ≈ 3.6 ms
混合压测（10 并发）：整体 P95 = 397 ms
```

**这两个数字不是一个东西。**

1. 混合 P95 是**所有场景的混合分布**。其中 `slow_report`（权重 10%）
   单场景 P95 就有 544ms，它必然把混合分位数拉高；
2. 混合口径**带并发**，含排队时间；单请求口径没有。

看到"报表 38ms，整体 P95 却 397ms"不是哪里算错了。
要解释混合数字，必须**先按场景拆开**
（`platform_cli run --scenario slow_report`）。

## 七、基线劣化只告诉"变慢了"，不告诉"为什么"

`R3-baseline-degradation` 能可靠地发现"这轮比基线慢 30%"。
它**不能**告诉你原因。

**归因要靠：**

1. 报告里的**场景拆解**（按权重分开压，看是哪个场景在劣化）；
2. 对照两次运行的 **SQL 与执行计划**；
3. 必要时用 `--scenario X` 单场景复压，排除其它场景干扰。

门禁的 `action` 字段写的就是这个流程。

### 容忍带是本机环境的属性，不是通用常数

`DEGRADATION_TOLERANCE = 0.10` 是在**这台机器上实测**得到的
（`platform_cli noise --rounds 5` → 极差 8.16%、单轮最大偏离 4.95%）。

换一台机器、换容器、或 CI runner 被别的任务抢占，
这个量级就会变 —— 可能更好，也可能差得多。

**所以这份报告里的"持平/劣化"判定，只在这台机器上成立。**
到别处使用应当重跑 `noise` 重新定，而不是沿用 10% 这个数。

反过来说：一个比当地噪声还窄的容忍带**等于没有容忍带**，
它不会更严格，只会稳定产出假阳性。

## 八、还有哪些没做

如实列出，避免被当成"这些也已经有了"：

| 项 | 状态 |
|---|---|
| 分布式压测 | ❌ 未做（单机线程池） |
| 流量录制回放（GoReplay/Diffy） | ❌ 未做 |
| Prometheus + Grafana 看板 | ❌ 未做（自研 SVG 看板） |
| 消费者驱动契约测试（Pact 双向） | ❌ 未做（只有 response schema 校验） |
| 混沌工程 / 故障注入 | ❌ 未做 |
| 全链路追踪（trace 级归因） | ❌ 未做 |
| 生产环境真实流量对照 | ❌ 未做（全部是合成流量） |

**合成流量的局限：** 本项目的全部流量都是按权重生成的合成流量，
不是真实回放。真实流量的参数分布、热点集中度、
以及"同一个用户连续操作"的会话特征都不一样。
**这是与生产最本质的一处差距。**

---

## 九、一句话总结

> 本平台擅长回答"**变了没有、变成什么样**"，
> 不擅长回答"**生产环境到底能扛多少**"。
>
> 前者靠相对比较，单机就能做可靠；
> 后者需要真实环境、真实流量和分布式压力源。

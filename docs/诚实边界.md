# 诚实边界

这个文件说明**这套平台能证明什么、不能证明什么**。

它不是免责声明，是使用说明。**越界解读比没有数据更危险** ——
一份"P95 = 397ms"的报告，配上错误的适用范围，会变成一次
基于错误信心的架构决策。

---

## 一、绝对数字不能外推，比例关系可以

### 不能做的

- ❌ 拿本机的 RPS 数字做容量规划
- ❌ 拿本机的 P95 断言"生产环境会遇到 X ms"
- ❌ 对比本机数字和别人的 benchmark 报告

### 可以做的

- ✅ 同一个接口两种实现的**比例**（N+1 比聚合慢 7.8×）
- ✅ 改前改后的**相对变化**（这次提交让 P95 劣化了 30%）
- ✅ 不同场景之间的**排序**（写路径比读路径慢一个数量级）

### 原因

压测机与被测服务**跑在同一台机器、抢同一份 CPU**。
自研引擎是进程内线程池，被测服务也是本机进程 —— 两边互相干扰。

真实容量会比这里高（服务能独占资源）。
但两个接口之间的相对开销是真实的，因为干扰对双方是均等的。

## 二、单机引擎是天花板：没有分布式能力

自研引擎（`bench/engine.py`）用 `ThreadPoolExecutor` 在本机发起压测。

**这意味着：**

- 压到几千并发时，瓶颈很可能是**压测机自己**，不是被测服务；
- 单机线程池到不了生产级别的压力上限（万级并发需要分布式压测集群）。

**平台自己的应对：** `Runner` 会采样实际在途请求数（`max_inflight`），
当"实际在途 < 配置并发的一半"时会提示**瓶颈在压测机**。

实测中每个梯度的 `inflight` 都等于配置并发（10u → inflight=10，
20u → inflight=20），说明**在本次实测的压力范围内**压测机还不是瓶颈。
但这是"本次实测范围内"的结论，不是"这个引擎永远够用"。

## 三、SQLite：写路径的数字完全没有参考价值

这是本项目**最容易被误读**的一组数字。

### 现象

10 并发混合压测下：

| 场景 | RPS | P95 | P99 |
|---|---:|---:|---:|
| `item_detail`（读） | 843 | 36.0 ms | 61.5 ms |
| `stock_write`（写） | **66** | 403.9 ms | **915.5 ms** |

写路径比读路径慢一个数量级以上。

### 但这不是"代码写得差"

瓶颈是 **SQLite 的单写者模型**：写操作走 `BEGIN IMMEDIATE`
（独占写锁），写请求之间**必须串行化**。并发再高也不会变快，
只会让更多请求排队。

### 所以

- ❌ 不能说"这个应用的写接口性能有问题" —— 换 MySQL/PostgreSQL 后
  写并发模型完全不同，这组数字**没有参考价值**；
- ✅ 可以说"在 SQLite 上，写路径是不可外推的瓶颈，容量评估必须
  在有真实数据库的环境里重做"。

**这条边界本身是有价值的结论** —— 它防止有人拿这组数字去
优化应用代码（那样做会一无所获，因为瓶颈不在代码里）。

## 四、性能探针的数据量必须接近真实规模

### 同代码、同机器、只换数据量

| 数据量 | `agg` | `n1` | 比值 |
|---:|---:|---:|---:|
| 800 | 5.5 ms | 11.4 ms | **2.08×** |
| 2 000 | 6.7 ms | 19.6 ms | 2.91× |
| 20 000 | 40.6 ms | 316.9 ms | **7.81×** |

**口径**：同机（Windows 11 / Python 3.12.10）、同一轮、SUT 进程复用连接 +
热身 3 次 + 15 样本取中位数，每格独立复测 3 轮取中位；本表的数再对
**6 次独立整轮复测取中位**（测量日期 2026-10-13）。原始输出
`C:\Users\lefan\DSH_project\DH_1\_measure\raw.txt`（仓库外，不随仓库提交）。
20 000 档与 `README.md` §1/§2、`docs/已知问题.md` P-1 是**同一组数字**。
**绝对值不可外推** —— 本机 6 次复测里 20 000 档 `agg` 37.1–54.3 ms、
`n1` 252.5–404.3 ms（极差约 60%）；能外推的只有比值随数据量放大的**趋势**。

> 这张表以前不是单调的：老版本写 `800 → agg 31.7 ms / n1 32.4 ms（1.02×）`，
> 而 `2 000 → agg 6.0 ms` —— 数据翻倍反而快 5 倍，物理上不可能。
> 成因是**两套测量口径混进了同一张表**：800 档用的是"每请求新建连接、不热身"
> 的老口径（约 10–25 ms 的建连固定成本压在 agg 的 ~5 ms 稳态耗时上，
> 把比值稀释到 1.02×），2000 档用的已经是热身后的稳态值。
> 老口径的数字本身没错，错在把它和新口径并排放进一张表。
> **那套老口径已从所有结论表里撤掉**，只在下面第五节作为教学案例出现。

N+1 的代价正比于"每个供应商下挂的物料数"。
800 条时每个供应商下只有 20 个物料，多查 20 次还不到把 SQLite 页缓存压垮的量级，
所以只有 2.1×；到 20 000 条放大到 7.8×。

### 所以

- ❌ 不能用小数据量的绿灯证明"没有性能问题"；
- ✅ 性能用例的数据量要接近真实规模（本项目用 20 000 条）；
- ✅ 功能用例可以继续用小数据量（800 条，跑得快）——
  但要清楚它**只验证功能，不验证性能**。

这也是性能探针从功能用例中拆出来单列 `tests/test_probes.py` 的原因。

## 五、测量方法本身会改变结论

### 不热身 vs 热身

同一个"报表比点查慢 5 倍"的断言，两套口径量出来的结论相反。

下面这组是**历史事故的原始数字**（探针最初红过的那一次，保留作调试记录）：

```
不热身、不复用连接：点查 15.7 ms / 报表 47.2 ms   → 3.0×   ❌ 红（当时）
```

2026-10-13 用同机对照实验把两套口径各量了一遍（20 000 条，`agg` 模式，
点查 `/api/items/1` 与报表 `/api/reports/slow-by-supplier` 在**同一个 SUT 会话内配对采集**，
每格 3 轮 × 15 样本取 3 轮中位；原始样本见仓库外 `_measure/raw.txt` 第十一部分）：

```
旧口径（每请求新建连接 + 不热身）：点查 16.3 ms / 报表 52.7 ms  →  3.2×
新口径（复用连接 + 热身 3 次）    ：点查  4.5 ms / 报表 55.0 ms  → 12.1×   ✅ 现行口径
```

（同一次配对采集里的两个口径，**不是**第四节那张结论表；结论表的数字是
6 次独立整轮复测的中位数，见下。）

差别几乎全在**分母**：换口径后点查从 4.5 ms 抬到 16.3 ms（**×3.6**），
而报表 55.0 → 52.7 ms（**×0.96，在噪声内基本不变**）。
冷启动时每个接口都背约 12 ms 固定成本（TCP 建连 + 页缓存冷 + uvicorn 惰性导入），
这个固定成本是**加法**不是乘法，所以它对快接口的相对抬升远大于对慢接口的，
**比值被系统性地压低了**（12.1× → 3.2×）。

这也正是旧口径被放弃的理由：它**不是"另一个同样有效的视角"**，
而是一个会给每个接口加一笔固定成本的坏口径；而且这笔成本在小数据量档
（800 条时 `agg` 稳态只有约 5.5 ms）会把比值稀释到接近 1×，
造出"数据翻倍反而更快"的物理上不可能的数字（见第四节）。
旧口径数字**不再作为并列的另一组数字**出现在任何结论表里。

### 所以

- ❌ 不要用"没热身的一次测量"去否定或肯定一个比例型结论；
- ✅ 比例型断言对测量方法极度敏感，热身、连接复用、样本量
  都要在报告里写清楚，否则数字不可复现；
- ✅ 当断言和预期不符时，**先怀疑测量方法，再怀疑被测对象**
  （本项目的三条探针里有两条最初都是测量方法的问题，不是服务的问题）。

## 六、混合场景分位数不能和单请求耗时比较

```
单请求（无并发）：  报表 ≈ 40.6 ms，点查 ≈ 4.2 ms
混合压测（10 并发）：整体 P95 = 397 ms
```

**这两个数字不是一个东西。**

1. 混合 P95 是**所有场景的混合分布**。其中 `slow_report`（权重 10%）
   单场景 P95 就有 544ms，它必然把混合分位数拉高；
2. 混合口径**带并发**，含排队时间；单请求口径没有。

看到"报表 40.6 ms，整体 P95 却 397 ms"不是哪里算错了。
要解释混合数字，必须**先按场景拆开**
（`platform_cli run --scenario slow_report`）。

## 七、基线劣化只告诉"变慢了"，不告诉"为什么"

`R3-baseline-degradation` 能可靠地发现"这轮比基线慢 30%"。
它**不能**告诉你原因。

> **在 CI 上它连"变慢了"都不能可靠地说。** 容忍带 10% 是在**开发机**上按
> P95 的轮间波动定的（`CV_diff ≈ 4.40%`）。同一份配置在 runner 上连跑 4 轮，
> 单轮 CV 是 p95 11.7% / p99 39.0% / max 54.1% —— 容忍带对尾部指标只剩
> 0.18σ / 0.13σ，3 轮 3 红，红的项每次还都不一样。所以 CI 上 R3 显式带
> `--r3-advisory`：**照旧判、照旧打印，但不拦人**，因为那里的结论
> 分不清劣化与噪声。阈值一个字没改。详见 `docs/已知问题.md` P-16。
> 本机（这台开发机）上的 R3 行为不变，仍是 blocking。

**归因要靠：**

1. 报告里的**场景拆解**（按权重分开压，看是哪个场景在劣化）；
2. 对照两次运行的 **SQL 与执行计划**；
3. 必要时用 `--scenario X` 单场景复压，排除其它场景干扰。

门禁的 `action` 字段写的就是这个流程。

### 而且它只在"两轮是同一套实验"时才说话

这是这一轮补上的一道诚实性：基线现在连**配置快照**一起存
（`items` / `report_mode` / `scenario` / `step_users`），比之前先判可比性。
两轮配置不同（或老基线没有快照）时，R3 输出的是 `[SKIP] 无法判定可比性`，
**不输出劣化百分比**。

为什么宁可"不下结论"：真实发生过 baseline `items=5254 / 并发 20`、
current `items=900 / 并发 80`，报告打出 `p95 +40.0% 劣化`。
数字都算对了，结论是假的 —— 而一个假的红色结论会让人去查
根本不存在的性能问题。

代价是：**老基线（没有配置快照的）第一次跑会变成 SKIP**，
需要重建一次基线才能恢复判定。这是有意选的默认方向：
"无法判定"比"看起来判定过"更诚实。

### 容忍带是本机环境的属性，不是通用常数

`DEGRADATION_TOLERANCE = 0.10` 是在**这台机器上实测**得到的
（`platform_cli noise --rounds 5` → 5 轮 P95 均值 131.4ms、样本标准差
4.09ms → 单轮 CV 3.11% → 两轮差值的 `CV_diff = √2 × CV ≈ 4.40%`，
10% ≈ **2.27σ**）。

这里有两点必须如实说：

- **2.27σ 是工程折中，不是统计保证。** 它对应的单尾假阳性率约 1.2%，
  不是 0。想把假阳性压到真正的 3σ 水平，需要把带子放到 ≈13.2%，
  代价是漏报更多 —— 这个取舍不替使用者做。
- **它只在这台机器上成立。** 换机器、换容器、或 CI runner 被别的任务抢占，
  这个量级就会变 —— 可能更好，也可能差得多。

**所以这份报告里的"持平/劣化"判定，只在这台机器上成立。**
到别处使用应当重跑 `noise` 重新定，而不是沿用 10% 这个数。

反过来说：一个比当地噪声还窄的容忍带**等于没有容忍带**，
它不会更严格，只会稳定产出假阳性。

### 临时目录会被删掉，所以日志要趁早看

`start_sut` 自建的临时库与日志目录现在由 `SutHandle.stop()` 回收
（调试时可传 `keep_tmp=True` 保留）。这意味着**一次运行结束之后，
日志就没了** —— 想复盘就只能在运行过程中或保留模式下取。
这是刻意的取舍：此前不清理，系统 Temp 下累积了 289 组 `perf-sut-*`。

## 八、还有哪些没做

如实列出，避免被当成"这些也已经有了"：

| 项 | 状态 |
|---|---|
| 分布式压测 | ❌ 未做（单机线程池） |
| 流量录制回放（GoReplay/Diffy） | ❌ 未做 |
| Prometheus + Grafana 看板 | ❌ 未做（自研 SVG 看板） |
| 消费者驱动契约测试（Pact 双向） | ❌ 未做（只有 response schema 校验） |
| 混沌工程 / 故障注入 | ❌ 未做 |
| 全链路追踪（trace 级归因） | ❌ 未做 |
| 生产环境真实流量对照 | ❌ 未做（全部是合成流量） |

**合成流量的局限：** 本项目的全部流量都是按权重生成的合成流量，
不是真实回放。真实流量的参数分布、热点集中度、
以及"同一个用户连续操作"的会话特征都不一样。
**这是与生产最本质的一处差距。**

## 九、一句话总结

> 本平台擅长回答"**变了没有、变成什么样**"，
> 不擅长回答"**生产环境到底能扛多少**"。
>
> 前者靠相对比较，单机就能做可靠；
> 后者需要真实环境、真实流量和分布式压力源。

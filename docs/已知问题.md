# 已知问题清单

这份清单是这个项目的**核心资产**，不是待办事项。

性能平台的难点从来不是"发现慢"，而是**证明自己真的能发现慢**。
一个从没拦下过任何东西的门禁，和没有门禁的区别只是多花了几分钟 CI 时间。
所以这里维护的是一批**故意存在的、可复现的缺陷**，每个都配有探针用例，
用来反复证明"门禁确实会红"。

清单到期日是明确的：**缺陷被修好那天，对应的探针会变红**，
提醒去更新这份文档和 `gate_rules.yaml`。

## P-1　`/api/reports/slow-by-supplier` 的 N+1 查询

**状态**：存在（探针：`tests/test_probes.py::test_probe_n1_is_slower_than_agg_at_realistic_scale`）

**位置**：`sut/app.py` 的 `slow_by_supplier()`，`mode=n1` 分支

**机制**：先查出供应商列表，再对每个供应商查一次物料、对每个物料查一次流水。
查询次数 = 供应商数 × 每个供应商的物料数。这是一个真实的、
在 Code Review 里极常见的写法 —— 它不报错、小数据量下也不慢。

**实测**（20 000 条物料，本机，双方均热身 3 次）：

| 实现 | 耗时（中位数） | SQL 查询次数/请求 |
|---|---:|---:|
| `agg` | 38.2 ms | **1** |
| `n1` | 219.2 ms | **20 040** |

**比值 ≈ 5.7×（单请求）**。

### 真正的杀伤力在并发下，不在单请求

单请求 5.7× 其实还算"能忍"。把并发拉起来之后，n1 的表现是**崩溃**：

| 并发 | `agg` 耗时 | `agg` RPS | `n1` 耗时 | `n1` RPS |
|---:|---:|---:|---:|---:|
| 1 | 37.1 ms | 27.1 | 218.9 ms | 4.59 |
| 4 | 57.5 ms | 69.8 | **2 451 ms** | 1.68 |
| 10 | 105.2 ms | 95.5 | **9 059 ms** | **1.08** |

`agg` 的耗时随并发**平缓上升**（37 → 58 → 105 ms，典型的排队），
吞吐从 27 涨到 96 RPS。
`n1` 的耗时**爆炸式增长**（219 ms → 2.4 s → 9.1 s），
吞吐反而**一路下跌**（4.59 → 1.68 → 1.08 RPS）——
并发从 4 涨到 10，吞吐还不如单线程。

**这是典型的"加并发反而更慢"**：20 040 条 SQL 轮番争抢
SQLite 的连接与页缓存，并发只是让它们互相踩踏。
如果只看单请求数字（5.7×），完全得不出"这个接口上线会挂"的结论 ——
**这正是为什么性能验证必须在并发下做，而不是量一次响应时间。**

### 为什么是 20 040 条 SQL

`N1_SUPPLIER_LIMIT` 默认 40，每个供应商下挂约 500 个物料
（20 000 / 40），再加每个供应商自己那 1 条查询：

    40 × (1 + 500) = 20 040

**这个数字随数据量线性增长**：物料涨到 40 000 条，
查询数就是 40 040 条。所以 N+1 不是"慢一个固定倍数"，
而是"数据越多，和聚合的差距越大"。

**这个缺陷最有价值的地方不是"慢"，而是"慢多少取决于数据量"**：

| 数据量 | `agg` | `n1` | 比值 |
|---:|---:|---:|---:|
| 800 | 5.5 ms | 13.4 ms | 2.43× |
| 2 000 | 6.9 ms | 19.7 ms | 2.87× |
| 20 000 | 49.0 ms | 379.9 ms | 7.75× |

（口径：同机同轮、复用连接 + 热身 3 次 + 15 样本取中位数。**绝对值随轮次浮动**，
能外推的是比值趋势；老版本这张表的 800 档 `31.7/32.4/1.02×` 是"每请求新建连接、
不热身"的另一套口径，与 2000 档的稳态值混排才显得非单调，详见 `docs/诚实边界.md` 第四节。）

在 800 条数据下这条探针**曾经红过**（老口径下比值 1.02），因为每个供应商下
只挂 20 个物料，多查 20 次被 SQLite 的页缓存完全吸收。
**在玩具数据量上做性能判断，结论会是"没有性能问题"。**
这比不测更危险 —— 它给的是一个一直持续到上线的虚假安心感。

**门禁**：`P1-n1-probe`（blocking，P95 > 150 ms）、`P2-n1-agg-ratio`（warning，比值 > 10×）；
外加两条前提类规则 —— `P0-probe-data-equivalence`（blocking，两个实现返回的数据必须一致）、
`P3-probe-sample-size`（warning，某一模式的样本数 < 2000 时拒绝让 P95 结论成立，见 P-7）。

## P-2　报表是全站最慢的读接口

**状态**：存在（探针：`test_probe_report_is_slowest_read_endpoint`）

**机制**：聚合要扫的行天然比点查多。这在业务上合理，
但它意味着**如果一个新功能要复用这个报表，成本会不成比例地被放大**。

**实测**（20 000 条，`agg` 模式，双方均热身 3 次）：点查 `/api/items/1`
**3.6 ms**，报表 **38.2 ms**，**差距 ≈ 10.7×**。

**这条用例本身就是一次测量方法的复盘**：它最初写成"不热身、直接打 15 次"，
量出 15.7 ms vs 47.2 ms 只有 3.0×，**于是用例红了**。
原因不是服务变快，而是不热身时每个接口都背上约 12 ms 的固定成本
（TCP 建连 + 页缓存冷 + uvicorn 惰性导入）。这个固定成本加在分母
（3.6 ms 的点查）上占比远大于加在分子（38 ms 的报表）上，
**比例被系统性地压低了**。

**教训：比例型断言对测量方法极度敏感，热身不足会低估真实差距。**

**门禁**：`R2-p95-absolute`（blocking，P95 > 300 ms）

## P-3　SQLite 单写者：写路径比读路径慢一个数量级

**状态**：存在（探针：`tests/test_sut_api.py::test_probe_write_path_slower_than_read_path`）

**机制**：写要走 `BEGIN IMMEDIATE`（独占写锁），且一个业务动作
（库存 +1 再 -1）包含两次往返。SQLite 的**单写者模型**决定：
写请求之间必须串行化，并发再高也不会变快。

**实测**（10 并发，混合读写压测）：

| 场景 | RPS | P95 | P99 |
|---|---:|---:|---:|
| `item_detail` | 843 | 36.0 ms | 61.5 ms |
| `stock_by_category` | 463 | 47.7 ms | 74.1 ms |
| `items_list` | 409 | 44.3 ms | 54.6 ms |
| `stock_write` | 66 | 403.9 ms | **915.5 ms** |
| `slow_report` | 21 | 544.0 ms | 562.2 ms |

**这条缺陷直接决定了平台的一条边界结论**：
`stock_write` 的瓶颈是 SQLite 的写锁，不是应用的代码质量。
在 SQLite 上量到的写路径数字**不能外推到 MySQL/PostgreSQL** ——
后者的写并发模型完全不同。报告里的"结论的边界"一节就是在说这件事。

## P-4　一个被真实抓出来的聚合扇出 bug（已修复）

**状态**：**已修复** —— 保留在清单里，因为它的发现过程比缺陷本身更有价值。

**这个 bug 不是特意造的**，是写 `agg` 实现时无意引入的，
而且它**骗过了当时所有的功能用例**：

```sql
-- 错误写法：三张表一路 LEFT JOIN 到底
FROM suppliers s
LEFT JOIN items i ON i.supplier_id = s.id
LEFT JOIN ledger l ON l.item_id = i.id
GROUP BY s.id
```

`ledger` 的 JOIN 会让每个物料**按它的流水条数重复出现**，
于是 `SUM(i.stock)` 把同一个物料的库存重复计了 N 次。
实测 20 条数据下：`stock_total = 113194`，真值是 `50697` —— **虚高 2.23 倍**。

**为什么难发现**：

1. SQL 语法完全合法，不报错、不警告；
2. 同一句 SQL 里的 `COUNT(DISTINCT i.id)` **因为有 DISTINCT 反而是对的** ——
   这种"一个指标对、另一个指标错"的混合状态，靠肉眼审 SQL 基本看不出来；
3. 它慢得不明显 —— bug 让结果变大，但 SQLite 的执行计划没变。

**抓到它的是一条交叉校验用例**，而不是速度断言：

```python
assert agg == n1, "agg 与 n1 返回的数据必须完全一致，否则性能对比不成立"
```

**这是整个项目最重要的一条方法论**：
性能对比的前提是**两种实现语义等价**。
如果 `agg` 和 `n1` 返回的数据不一样，那我们比的不是"同一个功能的两种写法"，
而是两个不同的功能 —— 速度对比立刻失去全部意义。
**所以性能平台必须先有数据一致性校验，再谈快慢。**

修复方式是把聚合的输入先收敛到正确的粒度（两个预先聚合的子查询再 JOIN），
而不是把 `SUM` 改成 `SUM(DISTINCT ...)` —— 后者会掩盖问题：
真正的教训是**聚合的输入必须先收敛**，否则 JOIN 扇出会静默污染
每一个非 DISTINCT 的聚合。

## P-5　压测脚本自己造出来的 28% 错误率（已修复）

这一类问题不属于"被测服务"，但**必须记在这里** ——
因为它伪装成被测服务的故障，比被测服务的真实缺陷更容易误导人。

### 现象

用 `--items 5000` 跑一轮混合压测，门禁输出：

```
[step]    5u    n=1424   rps=402.28   p95=41.22ms   err=28.72%
[step]   10u    n=1642   rps=465.60   p95=48.90ms   err=27.41%
[FAIL] R1-error-rate: 错误率 28.02%（阈值 1.00%）
判定：❌ 拦住
```

延迟一切正常（P95 只有 41ms），只有一个刺眼的错误率。
**看起来完全像"被测服务在某种并发下开始返回错误"。**

查错误分布才看出真相：

```json
{"status": {"200": 1000, "404": 409, "201": 15}, "error": {"HTTP 404": 409}}
```

**409 个 404**。不是 5xx，不是超时 —— 是请求打到了不存在的资源。

### 原因

`bench/scenarios.py` 里随机取物料 ID 的范围被**写死**成 `1..20000`：

```python
item_id = r.randint(1, 20_000)   # 错误写法
```

而 `--items 5000` 只灌了 5 000 条物料，ID 是 1..5000。
于是每次点查有 `(20000-5000)/20000 = 75%` 的概率打到不存在的 ID 上。

实测错误率 28% 而不是 75%，是因为混合场景里点查（30%）和写（5%）
两类才用这个 ID，其余场景不受影响 —— **比例也对得上**。

### 为什么这个 bug 特别值得记

1. **它伪装成被测服务的问题。** 结果面板上只有一个 `错误率 28%`，
   没有任何线索指向压测脚本。如果没有去查 `status_breakdown`，
   结论就会是"被测服务在高并发下有 28% 的失败率"——
   一个**完全错误且会被写进报告**的结论。
2. **它只在 `--items` 小于默认值时才出现。** 而 20 000 是这个项目的
   默认值，所以常规跑法（`--items 20000`）一直是全绿的。
   这种"默认参数下永远看不见"的 bug 最容易被长期保留。
3. **修法不是放宽阈值。** 错误率 28% 确实该拦住；
   错的是**造出这 28% 的人**。

### 修复

ID 范围由实际数据量决定，而不是由默认值决定：

```python
_ITEM_ID_MAX = 20_000                       # 默认值，用于单函数冒烟

def configure_item_range(item_count: int) -> None:
    global _ITEM_ID_MAX
    _ITEM_ID_MAX = max(1, int(item_count))  # CLI 在启动 SUT 后调用

def _random_item_id(r: random.Random) -> int:
    return r.randint(1, _ITEM_ID_MAX)
```

`platform_cli` 在 `run` 与 `probe` 中都显式调用
`configure_item_range(args.items)`。

**修复前后实测（`--items 5000`，其余参数不变）：**

| | 5u 错误率 | 10u 错误率 | 门禁 |
|---|---:|---:|---|
| 修复前 | 28.72% | 27.41% | ❌ 拦住（退出码 1） |
| 修复后 | **0.00%** | **0.00%** | ✅ 放行（退出码 0） |

### 防回归

`tests/test_engine.py`：

- `test_item_range_follows_configured_count` —— 配置 5 000 后范围必须变 5 000；
- `test_item_range_is_clamped_to_at_least_one` —— 传 0 不能让 `randint(1, 0)` 崩掉。

### 通用教训

> **压测工具凭空造出错误率，比它测不出问题更危险。**
>
> 看到一个无法解释的错误率时，先查 `status_breakdown` 分清
> 「4xx = 我自己发错了请求」和「5xx = 服务真的坏了」。
> 门禁 `R1` 的处理建议里写的就是这件事：
> "超时/连接被拒通常是容量问题，HTTP 5xx 是代码缺陷——
> 两者的处理方式完全不同，别混在一起改阈值。"


## P-6　`platform_cli.py prune` 是"改到一半"的：命令注册了但没有实现（已修复）

**状态**：已修复（本次修复补齐实现，未走"摘除"退路）

**位置**：`platform_cli.py` 的 `build_parser()`（prune 子命令注册）
与新增的 `cmd_prune()`

**机制**：`build_parser()` 里写了 `pn.set_defaults(func=cmd_prune)`，
但全文没有 `def cmd_prune`。Python 在**建解析器时**求值这个名字，于是：

```
$ python platform_cli.py --help
  File "...\platform_cli.py", line 800, in build_parser
    pn.set_defaults(func=cmd_prune)
NameError: name 'cmd_prune' is not defined. Did you mean: 'cmd_run'?
```

`build_parser()` 直接抛异常 ⇒ **10 个子命令全部不可用**，包括
CI 三个 job 依赖的 `suite` / `run` / `probe`。这不是"prune 坏了"，
是"CLI 起不来"。

按 `git show HEAD:platform_cli.py` 对照：HEAD 版本 534 行、0 处 `cmd_prune`；
工作区版本 721 行，但参数定义（`--keep-runs` / `--keep-days` /
`--dry-run` / `--no-vacuum`）和辅助函数（`add_json_flags` / `emit`）
都已写好 —— 是典型的"接口铺完了、实现没写"。

**实测**：

| | `--help` 退出码 | 测试 |
|---|---|---|
| 修复前 | `1`（`NameError: name 'cmd_prune' is not defined`） | `12 failed, 105 passed` |
| 修复后 | `0` | `118 passed` |

`prune --dry-run` 修复后输出（真实运行，`--keep-runs 2`，库里 6 个 `perf/lab`
运行 + 1 个 `running` + 1 个被基线引用）：

```
[prune] 保留策略：每个 label 最近 2 轮
[prune]   perf/lab: 共 6 轮，将要删除 3 轮，保留 3 轮（其中 1 轮因被基线引用而强制保留）
[prune] 合计：runs 3 / steps 3 / cases 0 / gate_results 3
[prune] --dry-run：没有真的删除任何东西。
```

**门禁**：`tests/test_cli.py::TestParserWiring`。这个类存在的理由正是
一次同类事故（`def cmd_gate(args):` 行被覆盖导致 `NameError`，
当时 84 条测试全绿却挡不住"CLI 起不来"）。本次把 `prune` 也加进了
`test_expected_subcommands_exist` 与 `test_help_renders_for_each_subcommand`
的参数化列表 —— 之前这两个用例的列表里**没有 prune**，
所以 `prune` 的接线坏了它们也不会红。

### 删除时必须绕开的三处陷阱

实现 `cmd_prune` 时踩到的三件事，都已写进函数 docstring：

1. **`baselines` 没有外键**。它按 `(kind, label)` 存一行、用 `run_id`
   指向基线那次运行。删掉那次运行后基线不会消失，只会剩下悬空的 `run_id`。
   由于 `R3-baseline-degradation` 是拿基线里的 `metrics_json` 做比较
   （不是拿 run 做 join），悬空基线**还能用**，但 `baseline show` 会指向
   一个查不到的 run。处置：**保留被基线引用的 run** ——
   基线是"故意留着的老数据"，比任何统计都重要。
2. **`gate_results` 没有外键、没有 `ON DELETE CASCADE`**。`steps` / `cases`
   会自动清（`connect()` 里 `PRAGMA foreign_keys=ON` 生效的前提下），
   但 `gate_results` 会留下来变成孤儿行，必须手工删。
   实测：删 20 轮时连带清掉了 5 020 条 `gate_results`。
3. **`status='running'` 的运行不能删** —— 另一个进程正在往里写。

另外 `VACUUM` **不能在事务里执行**，必须单开连接；实测 30 轮 +
5 030 条 gate_results 的库经 VACUUM 后由 4 218 880 字节降到 49 152 字节。
`--no-vacuum` 用于 CI（VACUUM 要重写整个文件、需额外磁盘空间、会锁库）。

### 通用教训

> **"接口铺好了"和"功能存在"是两件事，而前者会让后者看起来已经完成。**
>
> 参数、help 文本、辅助函数全都在，唯独少了那个函数体 ——
> 而且它坏的方式是"整个 CLI 起不来"，不是"prune 不能用"。
> 这次事故和 `cmd_gate` 那次是同一个形状，所以测试也留在同一个地方：
> **只测接线**（能建解析器、每个子命令的 `func` 可调用、`--help` 能渲染）。


## P-7　probe 路径的样本量校验缺失：一条 BLOCKING 规则建在 10 个样本上（已修复）

**状态**：已修复

**位置**：`platform_cli.py` 的 `cmd_probe()`、
`metrics/gate.py` 的 `evaluate_probe()`

**机制**：`evaluate_perf()` 里有 `R4-sample-size`（`min_total_requests`，
默认 2000），但 `cmd_probe()` 走的是
`gate.merge(data_report, gate.evaluate_probe(p95, rules))` ——
**从不调用 `evaluate_perf`**，而 `evaluate_probe` 的签名里根本没有
样本量入参。于是 probe 路径上的样本量校验是**零**。

现场（`ci_logs/…N_1_缺陷探针…txt`）：

```
[probe] mode=agg rps=95.00 p95=46.9ms  p99=50.0ms  err=0.00%
[probe] mode=n1  rps=1.32  p95=3828.6ms p99=3828.6ms err=0.00%
```

n1 是慢查询，4 并发 × 8 秒只跑出约 `1.32 × 8 ≈ 10` 个样本。
`p95 == p99 == 3828.6ms` 不是"长尾很集中"，是
`bench/engine.py` 的 nearest-rank 在 N < 20 时退化成取最大值。
`P1-n1-probe` 是 **BLOCKING**，也就是说：**一条拦截流水线的规则，
拿着 10 个样本的"P95"在下判断**。结论方向恰好对（3828.6ms 确实
远超 150ms 阈值），但这个数字不配叫 P95，而报告里对此只字未提。

**实测**（`evaluate_probe` 修复前后，同一份 p95 数据）：

| 调用 | 产出的规则 |
|---|---|
| 修复前 | `P1-n1-probe`, `P2-n1-agg-ratio` |
| 修复后（不传样本量，保持向后兼容） | `P1-n1-probe`, `P2-n1-agg-ratio` |
| 修复后（`sample_totals={"agg":760,"n1":10}`） | **`P3-probe-sample-size`**, `P1-n1-probe`, `P2-n1-agg-ratio` |

新增规则的输出：

```
[WARNING] P3-probe-sample-size: 样本量不足（建议每种模式 ≥ 2000 次）：agg 760 次，n1 10 次
[FAIL]    P1-n1-probe: N+1 报表 P95 3828.6ms（阈值 150.0ms）；
          ⚠ 本轮 n1 只有 10 个样本，该 P95 实为最大值，此判定不可作为最终依据
```

**处置口径与 `R4` 一致：`severity=WARNING`，不翻结论。** 两个理由：
样本少说明"这轮压测不够长"，不说明"系统坏了"（`R4` 早就为此定过调 ——
把它设成 blocking 会让"压测只跑了 8 秒"变成红色构建）；
而且这里真正要修的是**静默**，所以除了这条 WARNING，
`P1-n1-probe` 的结论本身也被显式标注"不可作为最终依据" ——
不静默放过，也不假装它没发生。

**门禁**：`P3-probe-sample-size`（warning）。样本量入参是可选关键字参数，
不传时行为与从前**逐字相同** —— 这是为了让既有的
`evaluate_probe({"agg":..., "n1":...}, RULES)` 调用方与
`test_merge_combines_reports` 的规则集合断言保持成立。


## P-8　取值失败时 `P0-probe-data-equivalence` 会整条静默消失（已修复）

**状态**：已修复

**位置**：`metrics/gate.py` 的 `evaluate_probe_data()`

**机制**：原代码是

```python
if agg_rows is None or n1_rows is None:
    return report  # 取不到数据时由别的规则去报错，这里不重复喊
```

注释里说"由别的规则去报错"，但**没有任何别的规则会替它报错** ——
返回的是空报告，`P0-probe-data-equivalence` 这个名字连出现都不出现。

讽刺的是，这条规则守卫的正是本项目**最有价值的发现**：
`P-4`（聚合扇出，`SUM(stock)` 虚高 2.23 倍，113194 对 50697）
就是靠 agg / n1 逐字段比对抓出来的 —— 而它
**不报错、不慢、功能用例全绿**，只有交叉校验能发现。

**实测**：`gate.evaluate_probe_data(None, None).results == []`，
合并后 `rule_ids == ['P1-n1-probe']`（P0 缺席）。
三份真实 probe 报告（`reports/probe-*.md`）里的门禁段都只有
`P1-n1-probe` 和 `P2-n1-agg-ratio` 两行，**没有 P0，也没有
"前提校验"小节**。

**修复**：产出一条 `skipped=True` 的结果 —— 它出现在报告里（标 `[SKIP]`），
但不进 `blocked`。取不到数不等于数据不一致，不该把 CI 判红；
但也绝不能长成"通过"的样子。为此 `RuleResult` 新增 `skipped` 字段，
`GateReport` 新增 `skipped` 属性，`blocked` / `failed` 都忽略 skipped。

修复后：

```
[SKIP] P0-probe-data-equivalence: 取不到 agg/n1 的响应体，本轮**没有校验**
       两种实现的数据是否等价（不是「一致」，是「没比」）
```

### 同时修掉的 LIMIT 不对称

**位置**：`sut/app.py` 的 `slow_by_supplier()`（agg 分支无 LIMIT、
n1 分支 `LIMIT N1_SUPPLIER_LIMIT`，默认 40）

`_row_diffs` 原来是"行数不同 ⇒ 不一致"，而 agg 侧无 LIMIT、n1 侧
`LIMIT 40`；`sut/seed.py` 恰好只造 40 个供应商
（`SUPPLIER_NAMES = [f"供应商-{i:03d}" for i in range(1, 41)]`），
所以两个数字**永远相等**，"行数不等"这条分支从来没被执行过 ——
该规则在当前数据下恒判一致。

一旦供应商多过上限（或有人把 `PERF_SUT_N1_SUPPLIERS` 调小到 40 以下），
旧逻辑会把一个**设计上的截断**直接说成"数据不一致"—— 那是误报。

**修复**：按 `supplier_id` 对齐，n1 覆盖的每一行都必须在 agg 里逐字段相等
（n1 少一行 = 真缺陷，照样报 BLOCKING）；agg 单方面多出来的行**单独计数**，
判 `skipped`（无法判定），并在结论里显式写出覆盖率。

> 为什么 agg 多出行判"无法判定"而不是"一致"：n1 因为自身缺陷漏掉末尾
> 一个供应商时，那行看起来**和被 LIMIT 截断一模一样**。既然分不清，
> 就不能用"一致"给一个没比完的结论盖章，也不能用"不一致"去误报设计截断。
> 覆盖率数字必须显式出现在结论里，让读者知道结论的边界在哪。

实测：

| 输入 | 修复前 | 修复后 |
|---|---|---|
| `agg=60行, n1=40行`（20 行只在 agg） | `passed=True`（静默判一致） | `skipped`，message 写明"另有 20 个供应商只在 agg 出现，数据等价性**无法判定**" |
| `agg=40行, n1=39行` | `passed=True`（！真缺陷被放过） | `skipped` + 覆盖率告警（不误判为 pass） |
| `agg=40行, n1=40行` 且逐字段相等 | `passed=True` | `passed=True`（不变） |
| 字段值不等 | BLOCKING `passed=False` | BLOCKING `passed=False`（不变） |

**门禁**：`P0-probe-data-equivalence`（blocking；取不到数或覆盖面不足时
降级为 `[SKIP]`/warning，不进 blocking）。


## P-9　空套件被判 100% 通过，且 `suite` 吞掉 pytest 退出码（已修复）

**状态**：已修复

**位置**：`metrics/gate.py` 的 `evaluate_suite()`、
`platform_cli.py` 的 `cmd_suite()` 与 `_case_summary()`

**机制**：两处口径叠加。

1. `evaluate_suite()`：`rate = (passed / total) if total else 1.0` ——
   `total == 0` 时**回落到 1.0**，于是 `0/0` 打印成
   `通过率 100.00% (0/0)` 且 `blocked=False`。
2. `_case_summary()`：`"pass_rate": round(passed / total, 4) if total else 1.0`
   —— 同一个"0 个用例 = 满分"的假设，第二处。
3. `cmd_suite()`：`proc.returncode` 只进了 `emit` 的 payload
   （`"pytest_exit_code": proc.returncode`），**从不影响返回码**，
   最后一行是 `return 1 if report.blocked else 0`。

后果：pytest 退出码 4（用法错误）或 5（没收集到用例）时，
`cmd_suite` 仍然 `return 0`，CI 判绿。而
`passed/failed/errors` 是从 `cases` 表里**数出来的**，
写表的是 `metrics/pytest_plugin.py`：插件没生效、`-p` 参数写错、
收集阶段就崩了，表里都会是 0 —— 光看表会安静地放行。

**修复**：

- `total == 0` 时 S1 判 **`skipped`（无法判定）**，message 为
  `没有跑到任何用例，通过率无法判定（不是 100%，也不是 0%）：0/0`。
  这是三态：0/0 既不是 100% 也不是 0%，它是"无法判定"。
  （`tests/test_platform.py::test_empty_suite_is_not_a_failure` 的
  docstring 早就写了"没跑到任何用例不该被算成 0% 通过率"，
  所以这里**必须**不是 FAIL 也不是 blocking —— 该用例的断言保持成立。）
- `_case_summary()` 的 `pass_rate` 在 `total == 0` 时改为 `None`，
  不再回落到 `1.0`。
- `evaluate_suite()` 新增可选 `exit_code` 参数，产出
  `S3-pytest-exit`（BLOCKING）：退出码不是 0/1 即判拦住；
  退出码为 1 但表里一条失败都没记下来（账本坏了）也判拦住。
- `cmd_suite()` 把 `proc.returncode` 传进 `evaluate_suite()`。

**实测**（真实运行 `platform_cli.py suite`，修复后）：

| 场景 | pytest 退出码 | `cmd_suite` 退出码 | 判定 |
|---|---|---|---|
| `tests/test_cli.py` 全过 | 0 | 0 | ✅ 放行（`[PASS] S3-pytest-exit: pytest 退出码 0`） |
| `-k __no_such_test__`（0 用例） | 5 | **1** | ❌ 拦住（`[SKIP] S1-pass-rate: …0/0` + `[FAIL] S3-pytest-exit: pytest 退出码 5`） |
| `--no-such-flag-xyz`（用法错误） | 4 | **1** | ❌ 拦住（`[FAIL] S3-pytest-exit: pytest 退出码 4`） |

**门禁**：`S1-pass-rate`（blocking；0 用例时降级为 `[SKIP]`）、
`S3-pytest-exit`（blocking）、`S2-flaky-budget`（warning）。


## P-10　看板的容忍带不读 `gate_rules.yaml`，与 CLI 口径分叉（已修复）

**状态**：已修复

**位置**：`dashboard/app.py` 的 `api_gate()`

**机制**：同一个响应里，两行连着写：

```python
deltas = analysis.compare_to_baseline(merged, baseline["metrics"])          # 没传 rules
report = gate.evaluate_perf(merged, baseline, deltas, gate.load_rules(...))  # 传了 rules
```

于是"哪些指标算劣化"用 `metrics/analysis.py` 的模块常量，
"拦不拦"用 YAML。CLI 的两处（`cmd_run()` 与 `cmd_gate()`）**都传了 rules**，
所以**看板和 CLI 可能给出不同的结论**。

**当前数值恰好相同**（YAML 的 `perf.tolerance.degradation_pct: 0.10`
与模块常量 `DEGRADATION_TOLERANCE = 0.10` 相等），所以这个缺陷
**当前不表现为数值分叉，是结构性的** —— 只要有人按业务把 YAML 调成 5%，
看板就会出现"`deltas` 说在容忍带内、门禁却判拦住"的自相矛盾结论。

**修复**：加载一次，两处共用。

```python
loaded_rules = gate.load_rules(rules or DEFAULT_RULES)
deltas = analysis.compare_to_baseline(merged, baseline["metrics"], loaded_rules) if baseline else []
report = gate.evaluate_perf(merged, baseline, deltas, loaded_rules)
```

**实测**（构造一份把 `degradation_pct` 改成 1% / 50% 的 YAML，
同一轮数据 `p95 +5%`、`rps -5%`，直接调真实的 `api_gate()`）：

| 传入的 rules | 看板兼容带 | 看板判劣化的指标 | CLI 同口径结果 |
|---|---|---|---|
| `degradation_pct: 0.01` | `0.01` | `p95_ms, p99_ms, mean_ms, max_ms` | 完全一致 |
| `degradation_pct: 0.50` | `0.50` | （无） | 完全一致 |

修复前，两行的容忍带都恒为模块常量 `0.1`，改 YAML 不会生效。

**门禁**：无独立规则；正确性由"看板与 CLI 必须单点定义口径"保证。
`tests/test_dashboard.py` 里有一条同精神的结构测试
（`TestMergeIsSingleSourced`：整轮汇总只能定义在
`analysis.merge_step_rows` 一处 —— 历史事故是看板把 RPS 写成各梯度相加、
凭空翻倍）。

**残留**：`dashboard/app.py` 页面正文里仍硬编码
`{analysis.DEGRADATION_TOLERANCE:.0%}`（"本平台的口径里 10% 以内算持平"）。
`api_gate()` 的**判定**已经读 YAML 了，但这行**文案**还是模块常量 ——
改了 YAML 之后页面会宣称一个与实际生效容忍带不同的百分比。
本次未改（超出派发范围），仅记录在此。


## P-11　门禁真的拦住时，`print(report.render())` 会因 GBK 控制台崩掉（已修复）

**状态**：已修复（`platform_cli.py` 新增 `_make_stdout_utf8()`，在 `main()` 里
第一时间把 stdout/stderr 切成 `utf-8` + `errors="replace"`）。

**位置**：`metrics/gate.py` 的 `GateReport.render()` 产出含 `❌` / `✅` 的判定行
（`HEAD` 版本里就已经有这两个字符，不是本次引入）；`platform_cli.py` 的
`cmd_run` / `cmd_probe` / `cmd_suite` / `cmd_gate` 都会 `print(report.render())`。

**机制**：Windows 控制台默认 GBK（`cp936`）。**只有门禁拦住的那条路径会崩**：
`render()` 在放行时渲染出的字符串里没有 emoji，所以本地一路绿灯时永远看不见；
一旦某次门禁真的拦住，`print` 抛 `UnicodeEncodeError`，进程带着**错误的失败原因**
退出 —— 外面看到的是"崩溃"，而不是"门禁拦住"，报告文件也写不完。

**实测**（修复前，构造一个 pytest 用法错误让本轮结论无效）：
```text
$ python platform_cli.py suite --label bad-suite --target tests/does_not_exist.py
[suite] 通过 0 / 失败 0 / 报错 0 / 跳过 0
Traceback (most recent call last):
  File "...\platform_cli.py", line 415, in cmd_suite
    print(report.render())
UnicodeEncodeError: 'gbk' codec can't encode character '\u274c' in position 427:
illegal multibyte sequence
```
修复后同一条命令：`EXIT=1`，stdout 正常打出
`判定：❌ 拦住（存在 blocking 未通过）`。

**门禁**：无独立规则（这是工具自身的可用性问题，不是被测服务的性质）。
回归由 `tests/test_cli.py::TestParserWiring` 的 `--help` 渲染参数化间接覆盖，
但那条路径不触发 emoji；真正的保护是 `main()` 里无条件 reconfig。

**教训**：与 `docs/incident-encoding-20261010/` 是同一类 —— 不报错、测试全绿，
直到某个平时走不到的路径才炸。**而且这次炸的时机最坏：门禁唯一有价值的时刻。**


## 清单的维护约定

1. **每个缺陷都有对应的探针用例**，探针断言"缺陷存在"。
2. **修好缺陷 → 探针变红 → 更新本文档 + `gate_rules.yaml`**。
   这是刻意的：让"修好了但没更新文档"变成一个会红的构建。
3. **新增性能缺陷必须同时新增探针**，否则门禁覆盖不到它。
4. 探针断言**性质**（"n1 明显更慢"），不断言**具体数字**（"n1 = 210ms"）。
   写死数字的用例换台机器就红，而会随机变红的用例
   唯一的结果是训练所有人忽略红灯。

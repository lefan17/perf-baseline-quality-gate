# 度量口径

这个文件说明**平台是怎么下判断的**。把它单独写出来的原因很实际：
**判断的口径比采集更容易出错，而口径错了没人看得出来。**

`10% 以内算持平`、`拐点的判据是每用户吞吐掉了 20%` ——
这些数字必须是代码里的一行（`metrics/analysis.py` 顶部的常量），
而不是某个人脑子里的印象。改这个文件就要改那些常量，
反之亦然。

## 一、分位数：为什么用 nearest-rank

```python
def percentile(values, q):
    idx = math.ceil(q / 100 * len(values)) - 1
    return sorted(values)[idx]
```

**永远返回一个真实观测值**，不做插值。理由：

- **可在面试/评审中解释。** "第 95 百分位是 412ms"——这个 412ms
  确实在样本里存在过，能指着它继续追问。线性插值出来的 411.7ms
  不存在于任何一次真实请求里。
- **误差方向是保守的。** nearest-rank 对小样本会取到更大的值，
  而不会把尖峰平滑掉。对"守住尾部"这个目标是安全方向。

**代价说清楚：** 样本少时 P99 和 max 可能相等
（100 个样本里，P99 按 nearest-rank 就是第 99 个 = 最大值）。
所以门禁 `R4-sample-size` 会警告样本 < 2000 的情况 ——
不是因为算法有问题，而是因为**样本少时分位数本身不承载信息**。

### 分位数不是一律取最大：尾比必须成对来自同一梯度

`_merge_from_rows` 不重算分位数（原始样本没有入库，入库的是汇总），
但它**不能简单地"每个分位各自取最大值"**。

`p50 / p90 / max` 各自取最差梯度确实保守。问题出在
**门禁 R5 用的是分位数之比 `P99/P95`**：

```
梯度1: P95 = 50,  P99 = 300  → 比值 6.00   （真实的长尾，必须拦）
梯度2: P95 = 200, P99 = 210  → 比值 1.05   （并发高了，整体平移，尾巴反而更短）

各自取 max  →  P95 = 200（来自梯度2）, P99 = 300（来自梯度1）
            →  比值 1.50  →  R5 判 passed
```

**两个数来自两个不同的梯度，这个比值不对应任何一次真实观测。**
它在分母上取了"最大的 P95"、分子上取了"最大的 P99"，两个方向都朝
"把比值压小"走 —— 所以"取 max"在比值上不是保守方向，而是**系统性掩盖**：
并发越高、延迟整体平移得越多，真实的尾比就越容易被抹平。

现在的口径：**尾比按梯度算，取比值最大的那一级的 P95/P99 成对输出**；
比值打平（浮点容差内）时取 P95 更大的那一级。`p50 / p90 / max` 仍各自取最大。

这条修法保住了原本想要的保守性（不会因为合并方式把劣化抹平），
同时让交给 R5 的比值是**某一次真实观测里发生过的比值**。
对门禁而言，宁可误报也不漏报。

### 整轮汇总只能有一个出口

这一条是踩出来的。曾经 `run` 走的是**另一条路**：
它手里还有原始样本，于是用 `merge_stats` 把所有梯度的样本
**池化**后重算分位数；而 `gate` 拿不到样本，只能 `_merge_from_rows` 取最大值。

同一个 run 于是有两个不同的 P95：

```
各梯度 p95 = [83.8, 128.9]
run 报告（池化）      = 105.9 ms
gate 判定（取 max）   = 128.9 ms
```

**报告上的数字和门禁据以拦人的数字对不上。**
这不会报错、不会变红，只会在某天有人问
"报告说 105.9ms 没超阈值，为什么这条流水线红了"的时候，
没人能解释到底哪个是真的。

现在统一走 `_merge_from_rows`：门禁与报告必然自洽。

### RPS 是"总请求数 / 总时长"，不是各梯度相加

同一个函数里还有一处静默错误：RPS 原先是
`sum(r["rps"] for r in rows)` —— 把各梯度的吞吐**加起来**了。
两梯度各约 370 RPS 的同一轮，汇总成 740，**凭空翻倍**。

它之所以能活很久，是因为门禁只在 RPS **下跌**时判劣化，
而"凭空翻倍"方向朝上，正好躲过检查。只有把多轮趋势放在一起看，
才会发现某轮吞吐高得没有道理。

现在按 `total / duration` 计算，`duration_s` 也随之进入汇总。

**教训：一个"取数函数"如果有两个调用方，就必须保证它们算出同一个数。**
两条路各写一遍合并逻辑，等于给未来埋了一个对不上账的雷。

## 二、基线劣化：容忍带与方向

```python
DEGRADATION_TOLERANCE = 0.10      # 10%
RPS_DEGRADATION_TOLERANCE = 0.10  # 10%
```

### 容忍带是量出来的，不是拍的

这个值最初写的是 3%（当"经验下界"）。**实测立刻证明它太紧。**

同一份代码、同一配置、连跑两轮：

```
第 1 轮   10u / 20k / agg   P95 = 105.9 ms   ← 设为基线
第 2 轮   10u / 20k / agg   P95 = 110.2 ms   ← +4.1%，门禁判「拦住」
```

**没有任何代码变慢，这是一次纯粹的假阳性。**

于是补了一个 `platform_cli noise` 子命令，把"拍一个数字"换成"量一个数字"。
本机实测 5 轮：

```
[noise] 各轮 P95：[128.5, 127.5, 137.9, 130.8, 132.2]
[noise] min=127.5 max=137.9 均值=131.4ms
[noise] 极差 = 8.16%（相对最小值）
[noise] 单轮最大偏离均值 = 4.95%
[noise] 建议 degradation_tolerance_pct ≥ 10
```

**把这批数换成统计量再看一遍**（均值 131.4 ms、样本标准差 4.09 ms）：

```
单轮 CV            = 4.09 / 131.4            = 3.11%
```

关键一步：**R3 判的是"两轮之差"，不是"单轮相对均值"。**
两轮独立同分布地抖动，差值序列的方差是单轮的两倍，于是

```
CV_diff = √2 × CV = 1.414 × 3.11% ≈ 4.40%
10% / 4.40% ≈ 2.27σ
```

也就是说，**10% 的容忍带约等于"两轮差值噪声的 2.3 倍标准差"**。

这里要如实说清两件事：

1. **8.16% 的极差不是推导依据。** 它只是同一批 5 个数的另一种描述，
   样本这么少时极差本身抖得厉害。真正决定假阳性率的是差值分布的标准差，
   所以推导走的是上面的 `CV_diff`。
2. **2.27σ 是工程折中，不是统计保证。** 它对应的单尾假阳性率约 1.2%，
   不是 0 —— 每跑一百次，仍可能有一两次是纯噪声触发的红灯。
   想要更硬的边界只有两条路，都不在本文件的自动范围内：
   多跑几轮把 CV 量准，或把容忍带放大到 3σ ≈ 13.2%（代价是漏报更多）。

**阈值数值本身没有因此改动**（仍是 10%）：改它会让 README 里所有历史结论
失去可比性，而这份文档的职责是把口径写清楚，不是替使用者拍板。

### 这里的教训比数字本身重要

**容忍带取决于机器和环境，不能凭常识填。**
它在共享 CI runner、容器、有其它进程抢 CPU 的机器上会完全不同。

所以：

- 换机器/换容器后应当重跑 `platform_cli noise --rounds 5` 重新定，
  **不要沿用别人环境里的值**；
- 一个比噪声还窄的容忍带**等于没有容忍带** ——
  它不会更严格，只会稳定地产出假阳性；
- 而稳定产出假阳性的门禁，唯一的结果是训练所有人忽略红灯。

`noise` **刻意不自动改 `gate_rules.yaml`**：
自动调阈值等于让门禁自己给自己发免死金牌。

### 方向不能一套公式

| 指标 | 变坏的方向 | 容忍带 |
|---|---|---|
| `p95_ms` / `p99_ms` / `mean_ms` / `max_ms` | **涨** | 10% |
| `error_rate` | **涨** | **0**（错误率没有"噪声"一说） |
| `rps` | **掉** | 10% |

RPS 的方向是反的：掉 10% 是劣化，涨 10% 是改善。
把它和延迟放进同一个公式里比较，会得到一个刚好相反的结论。

错误率的容忍带是 0：从 0% 涨到 0.5% 也是"服务开始报错了"，
不能和延迟抖动共用同一条带子。

### 先问「两轮是不是同一套实验」，再谈涨跌

容忍带解决的是"同样的实验，数字抖多少算正常"。
但如果**实验本身换了**，容忍带再宽也没用 —— 那时算出来的百分比
不描述任何东西。

真实发生过：baseline 是 `items=5254 / 最高并发 20`，
current 是 `items=900 / 最高并发 80`，报告照样打出
**"p95 +40.0% 劣化"**。两个数都算对了，结论是假的。

所以基线**连配置一起存**（`baselines.config_json`：`items` /
`report_mode` / `scenario` / `step_users`），比之前先做一次可比性判定。
三种结局，缺一不可：

| 结局 | 条件 | R3 的行为 |
|---|---|---|
| `ok` | 配置一致（`items` 相对差 ≤ 5%，`report_mode`/`scenario` 完全相等） | 正常判劣化 |
| `incomparable` | 数据量差 > 5%，或并发梯度最高级差 > 5%，或场景/报表实现不同 | **SKIP**，不给劣化百分比 |
| `unknown` | 基线（或本轮）没有配置快照（老数据） | **SKIP**，不给劣化百分比 |

**为什么"无法判定"必须显式存在**：它和"通过"在报告里必须长得不一样。
把不可比的两轮比出一个绿色结论，比不给结论危险得多 —— 前者会让人
以为已经检查过了。这里复用 `RuleResult.skipped`，语义与 P0/S1 的
"取不到响应体""0 个用例"完全一致：`passed=False`、`severity=warning`、
不进 blocked。

5% 这个阈值不是统计推导，是一条工程线：`items` 从 5000 变到 5100 是
同一次实验，从 5254 变到 900 完全是另一次。而 `report_mode`
（`agg` vs `n1`）与 `scenario` 一律要求**精确相等**，因为它们改的是
被测代码路径本身，差一点都不是噪声。

老库升级不需要重建：缺列由 `store._add_baseline_config_column()` 用
幂等的 `ALTER TABLE ... ADD COLUMN` 补上；补出来的老行是空快照，
于是读出来是 `unknown`（"无法判定"），而不是被当成 `ok` 默默放行。

### 边界取「不大于」，但要带浮点容差

容忍带的语义是"超过才算劣化"，即边界本身**不算**劣化。

这里有一个会稳定复现的坑：`100.0 * (1 + 0.10)` 在 IEEE 754 下是
`110.00000000000001`，于是

```python
(110.00000000000001 - 100) / 100  ==  0.10000000000000009   # 比 0.10 大！
```

结果"**刚好涨了 10.0%**"——最容易被反复触发的那个点——反而被判成劣化，
和 docstring 写的「边界取不大于」自相矛盾。

修法是在比较时加一个 `_EPS = 1e-9`：

```python
degraded = pct > tolerance + _EPS
```

**注意：这不是放宽标准，是让实现符合它自己声明的语义。**
把 `test_exactly_on_tolerance_boundary_is_not_degraded` 改写成
"从常量推导边界值"正是为了让它能测出这件事 ——
照抄数字的用例，在阈值变化时红得毫无信息量。

### 基线是 0 的时候

`pct = (current - 0) / 0` 在数学上是无穷大。直接格式化会输出 `+inf%`：

```
error_rate +inf%（基线 0.0）
```

技术正确，但对着这行字没人知道下一步做什么。
所以 `Delta.pct_text()` 在这种情况下返回**「从 0 变为 0.400」** ——
错误率从无到有，说清楚这件事比给一个无穷大符号有用。

## 三、拐点定位：判据是"每用户吞吐"而不是"总吞吐"

```python
KNEE_RPS_PER_USER_DROP = 0.20   # 每用户吞吐较峰值掉 20%
KNEE_ERROR_RATE = 0.01          # 或错误率 > 1%
```

**为什么看 `rps / users` 而不是 `rps`：**

总吞吐几乎总是随并发上升的（哪怕每个用户越来越慢），
所以拿总吞吐找拐点会一直找不到 —— 它会告诉你"再加人还能更快"，
直到服务彻底趴下。

`rps / users` 是**每用户得到的服务量**。它掉下来意味着
"加人已经不能按比例换来产出了"，这才是容量拐点的定义。

用实测数据看这个判据（`n1` 报表，20k 数据）：

| 并发 | RPS | **RPS/用户** | 相对峰值 |
|---:|---:|---:|---:|
| 1 | 4.59 | 4.59 | — |
| 4 | 1.68 | 0.42 | **−91%** |
| 10 | 1.08 | 0.11 | **−98%** |

按这个判据，拐点在 **4 并发**就已经越过了（每用户吞吐掉了 91%）。
总吞吐看则是"从 4.59 掉到 1.08"，同样能看出问题但是
**方向不明确**——而 RPS/用户 明确告诉你"每加一个人，人均产出在崩"。

### `last_stable_step`

返回拐点**前一级**。容量结论取这一级，而不是拐点所在的级别 ——
拐点那一级已经是"开始不划算"的地方，拿它当容量上限是自欺欺人。

## 四、flaky 识别：稳定度 + 最小样本

```python
FLAKY_MIN_RUNS = 6          # 少于 6 次执行不给结论
FLAKY_STABILITY_MAX = 0.85  # 稳定度低于 85% 判 flaky
```

**稳定度的定义：**

```
稳定度 = max(通过次数, 失败次数) / 总执行次数
```

即"多数派的占比"。全绿 = 1.0，全红 = 1.0，一半一半 = 0.5。

**注意全红也算"稳定"（稳定度 1.0）** —— 一个每次都失败的用例
不是 flaky，是一个坏掉的功能。这个区分很重要：
把"一直坏"混进 flaky 会掩盖真正的问题。

**判定条件（三个同时满足）：**

1. 执行 ≥ 6 次；
2. 既有通过也有失败（`passed > 0 and failed > 0`）；
3. 稳定度 < 0.85。

**样本不足时明确拒绝下结论**，而不是给一个不可靠的答案。
`analyze_flaky` 在样本不足时返回 `flaky=False` 并带上原因说明 ——
"没有结论"本身是一个有价值的结论。

### 稳定度是连续量：同一份历史，判定会随长度翻转

本项目**实测遇到过一次**，很值得记下来。同一个用例（写路径探针）
的 7 次执行历史，其中 6 次通过、1 次失败：

```
6P / 1F  →  稳定度 6/7 = 0.857  →  不判 flaky（0.857 > 0.85）
5P / 1F  →  稳定度 5/6 = 0.833  →  判 flaky    （0.833 < 0.85）
```

对，**同一批结果，只是多了第 6 个通过样本，结论就从"是 flaky"翻成"不是"**。

这不是 bug，是阈值判据的固有性质：0.85 这条线在小样本区间很密
（6 次里差 1 次就是 0.167 的跨度）。它带来两个实际后果：

1. **不要把 flaky 判定当布尔事实**，它是一个带样本量前提的统计倾向。
   报告里要带上 `6P/1F（稳定度 86%）` 这样的原文，而不是只给"是/否"；
2. **样本越多结论越稳**。`FLAKY_MIN_RUNS = 6` 是"可以开始看"的下限，
   不是"6 次就够定论"。

> 本例中的那 1 次失败，事后查明是**修复前**的一次历史记录
> （失败信息里还带着旧的 `tests/test_sut_api.py:244` 行号），
> 修复后的 6 次全部通过。这说明**历史数据的时效性**也是 flaky 分析的
> 一个隐藏变量：一条已经修好的老失败，会在统计意义上长期"污染"
> 某个用例的稳定度。真实的 flaky 平台需要有"按时间窗口过滤"的能力，
> 本项目目前只按最近 N 次执行取数，这个局限记录在此。

> **2026-10 后续**：这个用例后来又红过一次（CI 共享 runner 上
> 点查 2.2ms / 写 6.4ms = 2.88×）。根因还是"测量方法"这一类问题 ——
> 读路径耗时里混着约一半与写锁无关的固定成本，比值在负载变化时会摇摆。
> 修法同前：不改阈值，改测量口径（扣除固定成本），并补一条与机器速度
> 无关的并发不变量判据。详见 `docs/已知问题.md` P-3 与用例 docstring。

## 五、门禁：三档 severity 与"每条规则都要有行动指引"

```python
BLOCKING = "blocking"   # 拦住合并
WARNING  = "warning"    # 记录，不拦
INFO     = "info"       # 仅供参考
```

**为什么每条规则必须带 `action`：**

只会 `exit 1` 的门禁，寿命大约两周 —— 因为没人知道该做什么，
最后的结果是被注释掉。所以 `RuleResult` 把行动指引做成**必填字段**，
并且有一条测试专门检查这件事：

```python
def test_every_rule_carries_an_action():
```

这条测试不是在测代码，是在测**规则表有没有退化成一个只会变红的灯**。

**`R2` 绝对阈值的定位：** 它是兜底线，与基线无关。
存在的意义是防止"基线本身已经烂了"的情况 ——
如果某次把劣化后的结果设成了新基线，R3 就再也报不出来了，
这时 R2 还在。**绝对阈值和相对基线是互相兜底的两道网，缺一不可。**

**`R3` 无基线时是 `[SKIP]` + WARNING，不是 PASS，也不是 FAIL：**
首次运行没有基线是正常的，不该拦住任何人的第一次提交。
但**"跳过"必须在报告里长得和"通过"不一样**：曾经这里输出的是
`[PASS] R3-baseline-degradation: 未设置基线…`，于是"没比过"与
"比过了、没劣化"在日志里长得一模一样 —— 流水线上的 R3 就一直是这个状态，
而门禁的核心价值（抓"慢慢变慢"）从未生效却没有任何人看得出来。
现在它和 P0「取不到响应体」、S1「0 个用例」共用同一套 `skipped` 语义：
`passed=False`、`severity=warning`、`skipped=True`，看得见，但不进 `blocked`。
否则"忘了设基线"会变成常态，
而**没有基线的性能平台只是一个跑得慢的测试套件**。

## 六、场景权重：为什么写路径必须占一定比例

```python
DEFAULT_MIX = {
    "items_list": 40, "item_detail": 30, "stock_by_category": 15,
    "slow_report": 10, "stock_write": 5,
}
```

**只压读接口会得到一个过于乐观的结论。**

实测的混合压测（10 并发）里，各场景的表现差异巨大：

| 场景 | RPS | P95 | P99 |
|---|---:|---:|---:|
| `item_detail` | 843 | 36.0 ms | 61.5 ms |
| `stock_by_category` | 463 | 47.7 ms | 74.1 ms |
| `items_list` | 409 | 44.3 ms | 54.6 ms |
| `stock_write` | 66 | 403.9 ms | **915.5 ms** |
| `slow_report` | 21 | 544.0 ms | 562.2 ms |

`stock_write` 只占 5% 权重，却把混合 P99 拉到 916ms 附近。
如果配比里没有写请求，量出来的 P95 会好看得多，
而这个好看是假的 —— 生产流量里写请求一定存在。

**权重按真实读写配比来设**，不要为了数字好看而偏读。

## 七、一个容易误读的地方：混合 P95 ≠ 单请求耗时

单请求口径（无并发）：报表约 40.6ms，点查约 4.2ms。
混合压测（10 并发）：整体 P95 = 397ms。

**这两个数字不是一个东西，不能放一起比较：**

1. 混合 P95 是**所有场景的混合分布**，其中 `slow_report`（10% 权重）
   单场景 P95 就有 544ms，它必然把混合分位数拉高；
2. 混合口径**带并发**，含排队时间；单请求口径没有。

看到"报表 40.6ms，整体 P95 却 397ms"不要以为哪里算错了。
要解释混合数字，必须**先按场景拆开看**
（`platform_cli run --scenario slow_report` 就是干这个的）。

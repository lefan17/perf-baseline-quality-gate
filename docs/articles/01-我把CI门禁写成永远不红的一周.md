# 我把 CI 门禁写成「永远不红」的一周

我有两个仓库各自带门禁，这篇文章把两边的教训放在一起写：

- **性能门禁**（本仓）：12 条规则 R1–R5 / P0–P3 / S1–S3，判"性能有没有劣化"；
- **接口自动化平台**（另一个仓）：9 个 job，判"契约有没有漂移、用例有没有过"。

写它们的时候我以为最难的是"阈值怎么定"，事后发现不是。
最难的是：**你怎么知道门禁本身是活的？**

下面这七种形态，都真实发生过，其中五种是我自己写出来的。每一种的共同点是：
**CI 全绿，门禁什么都没拦。**

> 文中标注「本仓」的指性能仓，标注「平台仓」的指接口自动化仓；
> 文件名都给了完整路径，两个仓里同名不同物的东西不会混。

---

## 一、`--r3-advisory`：给规则装了一个开关，然后一直关着

R3 是"基线劣化"规则。它需要基线，而基线只在 CI 里生成。于是 workflow 里写了：

```yaml
python platform_cli.py gate --label ci-perf --r3-advisory
```

`--r3-advisory` 的含义是"这条规则只提示、不判红"。当时的理由是**基线还没稳**——
每个 PR 都在改 SUT，拿昨晚的基线判今天的 PR，红的人会觉得冤。

问题在于：**这个理由是有期限的，却没有任何机制提醒你到期。**
半年后回头看，R3 从来没有红过一次，而 README 里还写着"12 条规则会拦人"。

修法不是删掉 `--r3-advisory`，而是**让它按触发源分流**：

```bash
R3_FLAG="--r3-advisory"
if [ "${{ github.event_name }}" = "schedule" ]; then R3_FLAG=""; fi
```

PR 上仍然宽松（PR 本来就会改 SUT），**夜间回归必须严格**——那一轮跑的是 main，
基线就是它自己的历史，不存在"冤"的问题。

> 教训：**任何一个"临时放宽"，都必须同时写下它的到期条件。**
> 写在开关旁边不够，最好写成"在某条流水线上不放宽"。

## 二、`continue-on-error`：一条能吃掉任何规则的毯子

`continue-on-error: true` 是我最喜欢的 YAML 属性，也是我最容易滥用的一条。
它把"这一步失败了"降级成"这一步标黄了"，于是：

- UI 组测试：站点改版 → 34 条全红 → 加了 COE（**这个决定是对的**，见下）；
- `n1-probe` 探针步：数字抖动 → 加了 COE；
- `pages` 发布：网络抖动 → 加了 COE；
- `security-audit`：偶发超时 → 加了 COE。

四条 COE 叠起来的结果是：**12 条规则里只有 4 条真的能让流水线变红**。

我先写了个脚本把这件事说清楚，而不是靠自觉：

```python
# 平台仓：scripts/check_gate_policy.py
# 每条 continue-on-error 都必须登记在 docs/质量门禁策略.md 的表格里，并写清为什么放行
```

它做两件事：

1. 扫 workflow 找所有 `continue-on-error`（**job 级和 step 级都要认**——
   一开始只认 step 级，于是文档写"不阻塞"被误判 FAIL，写"阻塞"反而是假绿）；
2. 对照 `docs/质量门禁策略.md` 里的一段受控表格（`<!-- gate-policy:continue-on-error -->`），
   少一条登记就 FAIL。

于是"放宽"从"改一行 YAML"变成"改一处，还要解释"。

> 教训：**不要让放宽的成本低于解释的成本。** 否则放宽就是默认行为。

顺便说清楚 UI 那条为什么是对的：**一个无法区分"谁的错"的信号不该拥有阻塞权。**
站点是第三方的，它改版跟我们代码无关；把它设成阻塞，团队学会的第一件事就是
"红了就重跑"，然后所有门禁失去可信度。正确做法是把它移出阻塞链路，
**并在 README 里把口径写清楚**："9 个 job，其中 8 个阻塞 + 1 个只报告"。

## 三、跳过当通过：没有基线时 R3 报 passed

这是最隐蔽的一种。R3 需要基线，第一轮跑的时候没有基线，代码写的是：

```python
if baseline is None:
    return RuleResult(passed=True, detail="无基线，跳过")  # ← 灾难
```

结果：**没跑 = 通过**。第一次 CI 全绿不是因为性能好，是因为什么都没比。

修法是把"跳过"变成一种**独立于 passed 的状态**：

```python
return RuleResult(passed=False, skipped=True, detail="无基线，未做比对")
```

报告里打 `[SKIP]`，退出码不红，但**结论不是"通过"**。
区别在于：有人来问"这轮 R3 过了吗"，答案从"过了"变成"没比，因为没基线"。

> 教训：`passed / failed / skipped / error` 是四个状态，不是两个。
> 把它们压成布尔值的那一刻，你就造了一个永远绿的开关。

## 四、两个 job 都是绿的，数据却是空的

这条发生在平台仓，但它是我见过最难查的假绿。

现象：在线报表挂在 Pages 上，一直显示

```
累计轮次 0
用例级记录 0
各层概况（无数据）
```

排查了四层：

1. 我给 `pages` job 加的 `download-artifact` 步骤带 COE，但**门禁策略脚本要求每条 COE 登记**——
   于是 `pre-commit` job 红了（这条反而说明脚本是活的）；
2. `actions/upload-artifact@v4` 的 `include-hidden-files` 默认 `false`，
   而度量库在 `qaplat/.cache/`（点开头）→ **artifact 静默为空**；
3. 我为了排查加的 `ls -R | head` 在目录不存在时返回非 0，`set -o pipefail` 让整个 job 变红——
   **诊断步骤把自己弄红了**；
4. 真因：**整个 workflow 9 个 job 全是 `needs: None`，全部并行**。
   `pages` 在 `test` 上传 artifact 之前就去下载，报
   `Unable to download artifact(s): Artifact not found for name: qaplat-db`，
   拿空库渲染一张"累计轮次 0"的报表。

用 API 查那一轮 run 的 artifacts，发现 `qaplat-db: 23580 bytes` ——
**artifact 一直传成功了，只是下载得太早。** 修法：`pages` 加 `needs: [test]` + `if: always()`。

> 教训：**"两个 job 都是绿的，数据却是空的"比红灯难查一个数量级。**
> 排查顺序建议：先确认产物真的存在（API 看 size），再看消费时机（依赖图），
> 最后才怀疑路径与隐藏文件。

## 五、`python scripts/x.py | tee log` ：两层假绿叠在一起

这是我自己在 CI 里写的，一次踩两个坑：

```yaml
run: python scripts/proxy_probe.py --items 5000 | tee /tmp/probe.txt
```

步骤报 success，日志里却是：

```
File ".../scripts/proxy_probe.py", line 50, in <module>
    from bench.engine import Runner, Stats, run_api_call
ModuleNotFoundError: No module named 'bench'
```

两个原因叠加：

1. `python scripts/x.py` 的 `sys.path[0]` 是 `scripts/`，**不是仓库根**；
2. bash 没开 `pipefail` 时，管道的退出码取最后一个命令（`tee`）的 0。

修法三件套，缺一不可：

```yaml
env:
  PYTHONPATH: .
run: |
  set -euo pipefail
  python scripts/proxy_probe.py --items 5000 | tee /tmp/probe.txt
  grep -q "直连 SUT" /tmp/probe.txt      # 再加一条"输出真的出现"的断言
```

> 教训：**退出码为 0 只证明"进程没崩"，不证明"它做了事"。**
> 凡是"只发布数字、不下结论"的步骤，都要再断言一句关键输出存在。

## 六、门禁检查了一切，除了它自己

这个仓库的 core value 是"门禁不会说谎"。所以当我发现

```toml
files = ["bench", "metrics", "sut", "dashboard", "platform_cli.py",
         "scripts/proxy_probe.py", "scripts/distributed_run.py"]
```

——`scripts/check_*.py` 四个**门禁脚本自己**没有被 mypy 检查——我笑了很久。

理由写的是"要连着清一批存量问题，单独排期"。实测 `python -m mypy scripts/` 是
`Success`，**零错误**，那条注释早就过期了。

没纳入的代价不是"少检查几个文件"，而是**它们会悄悄退化**：
下一次有人在这四个脚本里写错类型，CI 不会说话。

> 教训：**"以后再补"的注释，要么带 issue 号，要么当天就删掉。**
> 它不会自己变成待办，只会变成一句谎言。

## 七、那怎么证明门禁是活的？

上面七条都是"事后发现"。正面回答这个问题只有一个办法：**造一条真红**。

`tests/test_r3_end_to_end.py` 干的就是这件事——它起**真的 CLI**、连**真的 sqlite**，
把基线改快 10 倍（也就是伪造一次"劣化"），然后断言两件事：

```python
assert "[FAIL]" in output
assert proc.returncode == 1
```

这条测试的价值不在于"覆盖了多少行"，而在于：**它证明了那条路径真的能红。**
一旦有人把 `--r3-advisory` 写死进去，这条测试立刻红。

配套的还有两条纪律：

1. **规则阈值全部外置**到 `gate_rules.yaml`，测试直接改 YAML 造红，而不是改代码；
2. **每条规则一个"必红"用例**：`R1/R2/R3` 各一条端到端，`S1/S3` 各一条单测。

## 收尾：一个自查清单

写完这七条，我把它压成了五问，贴在平台仓 `docs/质量门禁策略.md` 顶部
（性能仓对应的是 `docs/诚实边界.md` 与 `gate_rules.yaml` 的注释）：

1. **这条规则现在能让流水线变红吗？** 找一个最近的 run 证明，不要凭记忆。
2. **它的"放宽"有到期条件吗？** `--advisory`、COE、`xfail`，都要有。
3. **跳过时有独立状态吗？** `passed/skipped/error` 不能都压成 `True`。
4. **产物真的被消费了吗？** 两边都绿不等于数据到了。
5. **有一条测试能证明它会红吗？** 没有的话，它现在就是装饰品。

> 门禁的可信度不是"从来没红过"攒出来的，是**红过、而且红得对**攒出来的。
